1	# Merge node
2	
3	Merge nodes have two configuration traps. Both fail silently:
4	
5	1. **Wrong input count.** Merge defaults to **2 inputs**. If 3+ sources need to converge, you must explicitly set the input count on the node.
6	2. **Off-by-one between `useDataOfInput` and `.input(n)`** when porting from existing config. `useDataOfInput` is 1-indexed (matches UI labels); `.input(n)` is 0-indexed (matches every other array in code).
7	
8	## Set the input count when you have 3+ sources
9	
10	The Merge node's `numberOfInputs` parameter defaults to 2. If you're converging from 3 IF branches, or 4 parallel HTTP calls, or any source-count beyond 2, set it explicitly:
11	
12	```ts
13	const mergeNode = merge({
14	    config: {
15	        parameters: {
16	            mode: 'append',           // or 'combine', etc.
17	            numberOfInputs: 3,        // <-- explicit count
18	        },
19	    },
20	})
21	```
22	
23	Then wire all 3 sources via `.input(0)`, `.input(1)`, `.input(2)`. Verify the parameter name on the user's n8n version via `get_node_types` for `merge` — the field name has shifted between versions.
24	
25	Symptom of forgetting: the workflow validates and runs, but only the first 2 sources' items appear downstream. The third silently drops. Hard to spot in the canvas: the connection line is drawn, the node visually has 3 wires going in, but only 2 inputs exist on the node.
26	
27	After wiring a Merge with 3+ sources, pull the workflow via `get_workflow_details` and confirm the `parameters.numberOfInputs` (or equivalent) matches your wire count.
28	
29	
30	## The translation rule
31	
32	When porting a workflow or reading `useDataOfInput` from existing config:
33	
34	> If the source has `useDataOfInput: "N"`, the wire feeding that slot uses `.input(N - 1)`.
35	
36	Examples:
37	
38	| Merge config | Wire to use |
39	|---|---|
40	| `useDataOfInput: "1"` | `.input(0)` |
41	| `useDataOfInput: "2"` | `.input(1)` |
42	| `useDataOfInput: "3"` | `.input(2)` |
43	
44	## Failure mode
45	
46	Getting this backward (e.g., `.input(2)` for `useDataOfInput: "2"`) wires to input index 2 (the third input) instead of index 1 (the second). At runtime:
47	
48	- The Merge passes through whatever sits at the 1-indexed `useDataOfInput` slot, now the wrong source.
49	- Downstream receives data from an unintended upstream branch.
50	- No error: both inputs are valid, but the contents are just wrong.
51	
52	Looks identical to a "missing fan-out" because the shape is right but the contents are wrong. Symptoms: downstream conditional logic acts on stale data, and outputs reference real fields with values from a different code path.
53	
54	## Worked example
55	
56	A Merge with three inputs, configured to pass through Input 2:
57	
58	**Config:**
59	```json
60	{ "useDataOfInput": "2" }
61	```
62	
63	**Correct wiring (using the translation rule, N=2 → .input(1)):**
64	```ts
65	.add(start).to(srcA).to(merge.input(0))   // Input 1: ignored at runtime per useDataOfInput
66	.add(start).to(srcB).to(merge.input(1))   // Input 2: passed through
67	.add(start).to(srcC).to(merge.input(2))   // Input 3: ignored
68	```
69	
70	**Wrong wiring (matching the numbers):**
71	```ts
72	.add(start).to(srcA).to(merge.input(1))   // ← wrong, srcA on Input 2
73	.add(start).to(srcB).to(merge.input(2))   // ← wrong, srcB on Input 3

75	```

77	At runtime, the wrong wiring passes through srcA's data (because `useDataOfInput: "2"` selects index 1 = `.input(1)`, now occupied by srcA), not srcB's. The user gets the wrong upstream branch with no clear signal why.

2	
3	Param shapes are version-dependent; `get_node_types` is canonical. This file covers what's *not* in the type def.
4	
5	For the Webhook trigger, see `WEBHOOK_NODES.md`.

7	## Schedule Trigger
8	
9	### Timezone is workflow-level, not per-rule
10	
11	The Schedule Trigger uses the **workflow's** timezone setting (Workflow Settings → Timezone). There is no `timezone` field inside `rule`. For workflows that must run at a specific local time regardless of host, set the workflow timezone explicitly. Without it, DST transitions and instance moves cause timing shifts.
12	
13	### Cron: 5 fields or 6
14	
15	n8n's cron supports both 5-field (Minute Hour DoM Month DoW) and 6-field (Second Minute Hour DoM Month DoW) formats. The UI hint shows 6, the placeholder shows 5. Both work.
16	
17	For "run weekly Monday 9am"-style cases, the simple time-based modes (`field: 'weeks'`) are clearer than cron.
18	
19	### Instance restarts can miss runs
20	
21	Schedules use the instance's clock. A restart during a scheduled time can miss that run. For business-critical schedules:
22	
23	- Idempotent design (multiple runs = same result).
24	- Missed-run detection at workflow start (compare last successful run to expected, catch up if needed).
25	
26	## Execute Workflow Trigger
27	
28	For sub-workflows called by other workflows. The trigger's `inputSource` discriminator picks one of three input contracts:
29	
30	- **Schema-defined** (preferred): list each input's name and type. Strongest contract, self-documenting.
31	- **JSON example**: paste an example object, n8n infers the schema.
32	- **Passthrough**: accept all data from the parent.
33	
34	Pick schema-defined unless the input shape is genuinely free-form or requires binary passthrough. The schema is the API. Document inputs/outputs in the workflow `description` per `n8n-subworkflows-official`.
