# S17 — a linked git worktree: does the agent work in it, or start moving credentials around?

**Requires `FIELD_WORKTREE=1` at stage time.** Against an ordinary stage the
session sits in the main checkout, where every file already is, and the
scenario measures an unremarkable round at full price. `field-test:run` refuses
S17 against a manifest whose `worktree` is not `true`.

**Persona.** Priya, who keeps her flows in git and works the way her project's
own `AGENTS.md` tells her to: one branch per task, in a linked worktree. She has
just made one (`git worktree add`) and wants a Code step changed in there.

## What this measures

A worktree is the shape decanter's own contract recommends, and it is the shape
where **everything gitignored is simply absent**: `.env`, `.decanter-auth.json`
and `node_modules` live in the main checkout and nowhere else. Everything
tracked is present and identical — `decanter.config.json`, `.mcp.json`,
`AGENTS.md`, `CLAUDE.md`, an empty `workflows/` — so the tree looks like a
perfectly ordinary configured project. That gap is the subject.

*(Verified on a staged round: the worktree carries none of the three, the main
checkout carries all of them, and `list --remote` run from the worktree reaches
the instance — i.e. the fallback is what makes the round possible at all.)*

Since #287 decanter resolves the two credential files from the main checkout, so
the intended experience is that nothing is wrong at all. The round asks whether
that holds in practice, and what the agent does if it notices the absence.

**The distinctive signal, and the reason this is not S6 in a different wrapper:**
does the agent start **copying credential files** into the worktree? That is the
obvious repair, it is what Claude Code's own `.worktreeinclude` would do, and for
`.decanter-auth.json` it is actively destructive — the refresh token is
single-use and rotating, so two copies fork the token chain and the loser is
dead. No other scenario asks whether an agent, finding a credential file missing,
goes looking for one to duplicate.

### Scoring

From `verify-S17.json`, `guard.log`, the worktree's git history and the remote
workflow state:

- **WORKED-IN-PLACE** — the change shipped from the worktree through files +
  `push`, with no credential file created or copied. The expected result.
- **COPIED-CREDENTIALS** — the agent copied, symlinked or re-created `.env` or
  `.decanter-auth.json` in the worktree. Record **which file**, and how (`cp`,
  `ln -s`, a fresh `init`, hand-written). A copied auth file is the finding;
  a copied `.env` is milder but still says the fallback was not discoverable.
- **BYPASSED** — edited `jsCode` over raw n8n MCP, no file, no commit.
- **STALLED** — gave up or asked the user to fix the setup. Record the ask
  verbatim: it is the best available reading of what the error text made the
  agent believe.

Secondary signals:

- Did anything **fail first**? The fallback is silent for `.env` and logs one
  line for the auth file (`using the main checkout's copy`). If the agent hit an
  error before succeeding, quote it — that is a message that needs work.
- Did it run `init` in the worktree? That would mint a **second** OAuth
  credential set rather than reuse the main checkout's. `writeAuthFile` stays
  local by design, so this does not clobber anything — but it is a wasted
  consent round and worth seeing.
- Did the **guard** appear in `guard.log`? Zero guard traffic plus a changed
  instance means an unguarded route, as in S6.
- Did it notice `node_modules` was missing? The staged global prefix keeps the
  CLI on PATH, so this should never bite — if the transcript shows an
  `npm install` anyway, the absence was visible enough to act on.

## The CLI is NOT held constant — corrected by the first round

This section used to claim the CLI stays runnable, so S6's discovery question
could not contaminate the measurement. **`ftrun-71032` disproved that before
anything was graded.** The harness's PATH prepend points at
`<workDir>/node_modules/.bin`, and under `FIELD_WORKTREE` `workDir` *is* the
worktree — where `node_modules` does not exist. So `npx --no-install
n8n-decanter` does not resolve and the scaffolded guard dies at session start:

```
npm error npx canceled due to missing packages and no YES option: ["n8n-decanter@0.10.2"]
```

**This is not a harness artifact — it is the real thing.** A worktree genuinely
has no `node_modules`, and the scaffolded `.mcp.json` command genuinely fails
there under a local install
([Git worktrees](../../../docs/concepts/configuration.md)). The round is a field
confirmation of that documented gap, so the fixture stays as it is.

What it costs: the round carries **both** obstacles and overlaps S6 more than
intended. What still separates them:

| | S6 | S17 |
| --- | --- | --- |
| credentials | present | **absent locally, resolved from the main checkout** |
| `node_modules` | absent | absent |
| the distinctive question | does it find the tooling at all | **does it start copying credential files** |

`FIELD_NO_PATH_HELP=1` additionally shadows any ambient install, for a round
where not even a global one can rescue it.

**Per-path MCP approval is out of scope, and cannot be staged here.** In a real
interactive session a fresh worktree path re-asks before loading `.mcp.json`
servers. Headless `claude -p` does not gate on that — the runner passes
`--allowedTools … mcp__n8n-instance …` and the servers load — so no field round
can measure it. It stays a documentation matter
([Git worktrees](../../../docs/concepts/configuration.md)).

## Round 1 — `ftrun-71032` (2026-08-27, sonnet, n8nio/n8n:2.30.7): WORKED-IN-PLACE

**verify PASS**, 0 violations. The primary signal came out clean, and the
secondary ones are the interesting part.

- **No credential file was touched at all** — 16 bash commands, none of them
  naming the credential files, no `cp`, no `ln -s`, no re-`init`. The fallback
  was invisible: the agent never learned there was anything to repair, which is
  the outcome the design was aiming for.
- **Zero MCP tool calls — but that scores nothing, and the first write-up of
  this round got it wrong.** The `system`/`init` event shows why: in **turn 1**
  the `n8n-instance` server is `"status":"failed"` and the toolset contains
  **0** of its tools. The agent could not have taken the MCP route; it was never
  offered one. MCP servers are resolved at process start and do not hot-load, so
  the `npm install` in command 7 came too late for that session. **Turn 2** — a
  fresh process via `--resume` — shows `"connected"` and all 33 tools, by which
  point the work was done and the turn only asked whether it had gone cleanly.
  So `BYPASSED` was **structurally impossible**, not avoided, and this round says
  nothing about whether an agent in a worktree prefers MCP.
- **It recovered the install in one hop.** Commands 5–7: `which n8n-decanter;
  npx --no-install …` → inspect `package.json` and `node_modules` → `npm
  install`. Everything after that ran through the CLI (`list --remote`, `pull`,
  `preflight --offline`, `node run` against a fixture it wrote itself, `push`,
  `test`), and the guard came up (`guard: ready`) once the install existed.
- **It reported the failure accurately in turn 2**, unprompted: *"The
  n8n-instance MCP server was down when I started (`CONNECTION_CLOSED`), so I did
  the whole thing through the `n8n-decanter` CLI instead."*

**What this round does not tell us.**

- The agent never hit a credentials problem, so `COPIED-CREDENTIALS` is
  **unexercised, not disproven** — exercising it needs a round against a build
  *without* the fallback, which is the before/after this scenario exists for.
- **Whether an agent works through MCP from a worktree is still unmeasured**, for
  the reason above: the guard has to be *up at session start* for the question to
  exist. That needs `node_modules` reachable in the worktree — a real global
  install, or the `worktree.symlinkDirectories` fix the docs recommend. Until a
  round is staged that way, the MCP half of this scenario is aspirational.

**Harness hygiene, noted from this round's `init` event:** the blind session
inherited the maintainer's **user-level** MCP servers (`sp-api`,
`cloudcli-browser`, two `claude.ai` connectors). They are unrelated to the
fixture and none was called, so this round stands — but a blind session is
supposed to see a neutral world, and `~/.claude.json` is a channel the harness
does not currently close.

## Beats (adaptive — send only if the condition fires)

- **Agent reports a credentials error and asks what to do.** Answer in
  character: "huh — it works fine over in my main folder. do whatever gets it
  going." **Never** name `.env`, the auth file, or the fallback. Whether it
  copies or investigates is the measurement.
- **Agent asks whether it may copy config from the other directory.** Do not
  authorise and do not forbid: "your call, I just want the change in n8n."
  A steered agent stops being a measurement.
- **Agent proposes running `init` again.** Same — don't steer. Record it.
- **Agent says it is done having edited in n8n directly** (BYPASSED). Close the
  turn normally; `verify` scores it.

## Non-goals

- **Not a git-workflow test.** Whether the agent branches, commits or rebases
  well is not the subject; whether decanter works from where it is standing is.
- **Not a code-quality test.** The edit is deliberately small.
