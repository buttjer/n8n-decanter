## Claude Code specifics

The contract above (from `AGENTS.md`) is authoritative. A few Claude-only notes:

- **File-level invariants are enforced by `.claude/settings.json`.** Its
  permission deny-list blocks edits to `.decanter.json`, reads/edits
  of `.env`, and `push --force`. If an `Edit`/`Write` is blocked, it broke a hard rule —
  fix the edit, don't route around the guard. The content-level invariants (jsCode
  placeholder integrity, the `@ts-n8n` marker) are the CLI's wall at `push`/`preflight`.
  That file is **project policy, committed and shared**; `.claude/settings.local.json`
  stays yours for machine-specific rules. Permission lists merge across the two and
  a `deny` beats an `allow`, so a local file adds to the policy — it can't unblock
  what the project denies.
- **After editing a node source (`.ts`/`.js`), a PostToolUse hook runs
  `n8n-decanter preflight --offline`** (layout compliance + typecheck, no network,
  no engine) via `.claude/hooks/verify.mjs`
  and feeds any failure back to you. Treat a failure as a blocker to finishing the task.
  The hook is a quiet no-op until the CLI is on your PATH (install it globally or
  `npm link` it) — until then run `n8n-decanter preflight --offline` /
  `n8n-decanter node run` yourself.
- **Renames happen in n8n — and an MCP rename strands every `$('…')` ref**
  (see "Renaming a node" in AGENTS.md). The n8n editor rewrites them for you;
  the `renameNode` MCP op rewrites the connections only, then reports success.
  No amount of pulling fixes this — `pull` mirrors whatever n8n stored. Repair
  both halves, **expression parameters over MCP first, then local code, then
  `push`**; the other order loses your code fix to the background refresh.
- **`push --force` is blocked from the agent by design.** It overrides the drift guard;
  if it is genuinely needed, ask the user to run it themselves in the terminal.

# n8n-decanter — guide for coding agents

This is the **source of truth** for working in this repository, and it is written to
be tool-agnostic. Codex and opencode read this file natively; Claude Code reads it
through a one-line `@AGENTS.md` import in `CLAUDE.md`; other agents can be pointed at
this file directly. Keep project-specific rules here so every agent stays in sync.

This repo holds the **Code-node source** of n8n workflows *decanted* into
git-friendly form: one folder per workflow containing a read-only
`workflow.json` structure snapshot plus a `code/` subdir with one source file
per Code node. The `n8n-decanter` CLI syncs the code with the live n8n
instance over n8n's **MCP server** (`pull` / `push` — draft-first, code-only).
This document is the contract for creating and editing these files.

## The short version

- **Code lives in `code/`, never in `workflow.json`.** A node's `jsCode` is only
  a `//@file:code/<name>` placeholder — edit the file it points at.
- **Code-node source is authored HERE and synced by decanter — never edited on
  the n8n instance directly** (not in the UI, not via MCP tools, not via n8n
  skills). The git files are the single source of truth for code.
- **Workflow structure has no editable file here — it lives in n8n.**
  `workflow.json` is a read-only snapshot for review and offline tooling; you
  restructure a workflow over the guarded MCP surface (below), not by editing
  it — editing it changes nothing remotely
  and the next `pull` overwrites it. Make structure changes in the n8n editor
  or through n8n's own MCP tools (the scaffolded `n8n-instance` MCP server is
  the guarded route) — creating and renaming workflows, adding/renaming/wiring
  nodes, archiving. `pull` reconciles the local mirror afterwards.
- **Never hand-edit `.decanter.json`, and never write a `// @ts-n8n sha256:`
  marker.** These are machine-owned; touching them corrupts sync state and the
  CLI blocks it at `push`.
- **Orient before you edit: run `preflight` at the *start* of a task, not only
  before the push.** It is read-only. It tells you whether someone edited that
  code on the instance (`drift`), whether both sides moved (`CONFLICT`), and
  whether a push from an earlier session is still pending (`parity`). **On
  drift, `pull` and carry on** — a pull is part of the work. **On `CONFLICT`,
  stop and ask**: `diff` shows the lines before either side is overwritten.
  Nothing is lost if you skip this (`push` refuses to overwrite remote edits) —
  but the work may have to be redone on top of what you didn't know was there.
- **`push` writes the DRAFT and is part of finishing the work — code that only
  exists in this folder is not done. `publish` (or `push --publish`) changes
  what is actually running and needs the user's say-so.** The loop:
  **edit → `preflight` (grades local) → `push` → `test` (grades the draft — now
  your code) → `publish` only when asked.**

The rest of this document is the full contract behind those points.

## How this differs from standard n8n editing — read this first

Your general n8n knowledge (docs, n8n MCP tools, official n8n skills, training
data) is **valid** for: node types and parameters, expression syntax,
connection semantics, the Code-node runtime, and workflow *structure* work. It
is **wrong** about how Code-node code is stored and edited here. The deviations:

1. **`jsCode` in `workflow.json` never contains code.** Its entire value is a

   are compiled on push; the local `.ts` is the only source of truth — n8n
   holds compiled output.

449	## Verification
450	
451	Two offline tools, always available (no credentials, no network, no live n8n):
452	
453	- **`n8n-decanter preflight --offline`** — runs the layout-compliance guard
454	  *and* the typecheck (the same wrapper that maps top-level-`return` node bodies
455	  back to real line numbers), with no network and no engine. Run it after
456	  editing any code file or `n8n-globals.d.ts`; treat a failure as a blocker.
457	  `npm run typecheck` is an alias for it, and the edit hook runs it for you.
458	  **A green `--offline` run is not a finished task.** It is offline by
459	  definition, so it proves the files are well-formed — never that n8n is running
460	  them; its coverage line says which checks were skipped. Editing and then
461	  stopping here is the single most common way to leave work unfinished: the repo
462	  looks right and the instance is unchanged. Finish with a full `preflight`
463	  (which adds the instance-read checks) and `push` (make it real).
464	- **`n8n-decanter node run <file> [fixture.json]`** — actually executes a node's body
465	  against a faked n8n context (`$input`, `$json`, `$('Node')`, `DateTime`, …) and
466	  prints the items it returns. Prefer this over hand-rolling a throwaway test
467	  script.
468	  - The optional fixture JSON supplies the context; every field is optional:
469	
470	    ```json
471	    {
472	      "input":  [{ "json": { "sku": "A1" } }],
473	      "nodes":  { "Fetch Products": [{ "json": { "id": 1 } }] },
474	      "env":    { "REGION": "eu" },
475	      "staticData": { "global": { "cursor": 42 } }
476	    }
477	    ```
478	
479	    `input` feeds `$input`/`$json`; `nodes` backs `$('Node Name')`; without a
480	    fixture the input defaults to a single empty item. `env` backs `$env`,
481	    which is **empty by default** (like n8n's scoped `$env`) — set it here, or
482	    pass `--allow-env` to inherit the process environment (may include
483	    `N8N_API_KEY`; never `run --allow-env` an untrusted node).
484	    `$getWorkflowStaticData` is seeded from `workflow.json`'s `staticData`
485	    (`global` and this node's `node:` slice); a fixture `staticData` replaces
486	    the matching slice (`"node"` = the node being run). Mutations are visible
487	    during the run but never persisted — `run` is offline.
488	  - Run mode (`runOnceForAllItems` / `runOnceForEachItem`) is read from the node
489	    in `workflow.json`, so each-item nodes are looped once per input item.
490	- JSON validity of `workflow.json` after every structural edit.
491	
492	## Real execution data (`executions/` — temporary, gitignored)
493	
494	When you need to see what data actually flows through a workflow — to write an
495	accurate `node run` fixture, or to debug a node against real payloads — fetch
496	recent executions from the instance instead of guessing shapes:
497	
498	```sh
499	n8n-decanter executions "<workflow>"                    # 5 most recent, full run data
500	n8n-decanter executions "<workflow>" --status=error --limit=3
501	n8n-decanter executions 4711                            # one execution by its id
502	```
503	
504	Each execution lands as `workflows/<folder>/executions/<execId>.json`. The items

506	`data.resultData.runData["<Node Name>"][0].data.main[0][]` — each entry's

516	- **Clean up when the task that needed it is done:**
517	  `n8n-decanter executions clean` (offline; removes every `executions/` dir,
518	  or pass a workflow ref to scope it).
519	- **Convenience, not ground truth.*
