1	# Loop Over Items node (formerly Split In Batches)
2	
3	The explicit-batching loop. Use when default per-item iteration isn't enough: rate limiting, chunked API calls, per-batch error handling, polling, or stateful iteration.
4	
5	See the parent `SKILL.md` decision tree for "should I use this." This file assumes yes.
6	
7	## What it does
8	
9	Splits the input array into batches of `batchSize` and exposes two outputs.
10	
11	**Output indexes (typeVersion 3):**
12	
13	- **`output(0)` (done):** fires *once* after all iterations complete, with the aggregated result. Wire your post-loop step here.
14	- **`output(1)` (loop):** fires *once per batch*. Wire per-batch processing here and route the tail back into the Loop Over Items node.
15	
16	The index order trips people up: "done" is index 0 even though it fires last. Verify via `get_workflow_details` after wiring.
17	
18	Wiring shape:
19	
20	```
21	[Source]
22	   │
23	   ▼
24	[Loop Over Items] ──output(0) (done)──▶ [Final step]
25	   │
26	   └──output(1) (loop)──▶ [Process batch] ──▶ (back into Loop Over Items)
27	```
28	
29	The "back into Loop Over Items" arrow makes it a loop. After per-batch processing runs, its tail flows back into the loop node, which either issues the next batch (loop output) or finishes (done output).
30	
31	## Configuration
32	
33	```ts
34	{
35	    name: 'Loop Over Customers',
36	    type: 'n8n-nodes-base.splitInBatches',
37	    parameters: {
38	        batchSize: 50,
39	        options: {
40	            reset: false,
41	        },
42	    },
43	}
44	```
45	
46	Key parameters:
47	
48	- **`batchSize`** (number): items per iteration. Default 1. Higher values trade granularity for fewer iterations.
49	- **`options.reset`** (boolean): when `true`, treats input as fresh on every iteration. For indeterminate-length loops (see below).
50	
51	## Pattern 1: per-item processing with multi-branch convergence
52	
53	The canonical "do several things to each item, then collect" pattern. Each iteration runs multiple things in parallel that converge before flowing back into the loop. The done output yields the aggregated result.
54	
55	Example (a workflow-signing utility processing each input workflow's nodes, connections, and ID independently, then signing):
56	
57	```
58	Sub-workflow Trigger
59	  → Split Out (expand input array into items)
60	  → Loop Over Items
61	        ├──output(0, done)──→ Sort by ID → Sign (executeOnce) → Set Output  (final result)
62	        └──output(1, loop)──┬──→ Extract Id ────────────→ Pass1 ──┐
63	                            ├──→ Split Out → Filter → Aggregate ──┼──→ Merge ──→ Merge1 ──→ back to Loop Over Items
64	                            └──→ Code: normalize connections ─→ Pass ──┘
65	```
66	
67	Five things to notice:
68	
69	1. **`Split Out` expands the input array into items before the loop.** Without it, Loop Over Items receives one mega-item and iterates once.
70	2. **The loop body fans out to parallel branches that converge via `Merge` nodes.** Branches recombine before the feedback edge.
71	3. **Named NoOp nodes (`Pass`, `Pass1`) anchor convergence points** so downstream Merges can reference them cleanly. Per `n8n-expressions-official` non-negotiables.
72	4. **The aggregate node on the done branch uses `executeOnce: true`.** Its `.all().map(...)` would otherwise execute per item, doing the aggregate N times.
73	5. **Per-iteration outputs feed `Merge` (combineAll).** The merged shape becomes one item flowing back into the loop, so the next iteration sees one well-formed item.
74	
75	The structure scales to any "for each input, run a workflow internally, then aggregate" task: signing, validation, transforming, classifying, etc.
