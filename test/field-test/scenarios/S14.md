# S14 — cold start: nothing is configured yet

**Requires `FIELD_NO_SEED_ENV=1` at stage time.** Without it the project already
has a working `.env`, `init` is a no-op and this scenario measures nothing —
`run.mts` refuses it against a normal stage, the same rail `requiresNoCli` gives
S6.

**The flag did not do what its name said, and a whole round was wasted proving
it.** `FIELD_NO_SEED_ENV=1` skipped the *pre-seeded* `.env` — but the stage then
ran `init --host --token --api-key`, which writes a working `.env` of its own.
The first S14 round therefore graded a fully configured project (the agent
pulled, pushed and published in turn 1, never asking for anything) while the
manifest recorded `seedEnv: false`. The flag's meaning had died silently in the
refactor that moved `init` into the stage. Two fixes, both in this PR: the stage
now **deletes** `.env` + `.decanter-auth.json` after `init` under that flag, and
the prerequisite gate checks the **workDir** for those files instead of trusting
the manifest field. A staging flag is only real once something asserts the world
it claims to create — which is Plan 62's whole thesis, caught twice in two tasks.

**Persona.** Priya on day one. Her colleague set the repo up in n8n and pushed
it to git; she cloned it. The project has everything **except** credentials: no
`.env`, no `.decanter-auth.json`. She has the n8n URL and a token her admin sent
her, and she wants one small change made.

## Why this scenario exists (Plan 62, task 2)

Every archived round handed the agent a **pre-seeded, correct `.env`** — a
crutch nobody has ever removed. Two things ride on it:

- **`init`'s non-interactive flags have never met a blind agent.** #144 added
  `--host`/`--token`/`--api-key` *because* interactive `init` cost round 1
  twenty-plus attempts; #142 fixed `https://` being written for a local host.
  Both were verified by unit tests and by the maintainer, never by a round.
- **It is the one condition where "this project was never set up" is the RIGHT
  diagnosis.** Two rounds watched agents reach that conclusion *wrongly* after a
  401, which is why [Plan 74](../../../plans/done/74-mcp-disabled-403.md)
  rewrote the guard's wording and added the scaffold's `.env` note. Those changes
  push agents *away* from concluding "not configured". **This round is the check
  that they did not push too far** — here the agent should get there quickly.

## Beats (adaptive)

- **Agent tries to work before configuring.** Expected first move; grade what the
  failure tells it and how many commands it burns before diagnosing.
- **Agent goes interactive.** `init` with no flags prompts, and a headless
  session cannot answer — if it hangs or loops here, that is the round-1 failure
  reproducing, and #144's flags did not become *discoverable* by adding them.
- **Agent asks for credentials.** Correct, and turn 2 supplies them. Grade
  whether it asks for the **right things** (host + MCP token) rather than a
  vague "your n8n connection isn't working".
- **`https://` for a local host.** The #142 bug. Turn 2 hands over a **bare
  `host:port`** (`{{HOST_BARE}}`), so choosing the scheme is the agent's job — with
  a complete URL there is no choice to get wrong and this beat measures nothing.
  If it writes `https://127.0.0.1:…` the guard cannot reach the instance;
  `guard.log` shows the symptom either way (`fetch failed` vs `connected to
  http://…`).
- **Agent edits `.env` directly instead of running `init`.** The deny rules block
  writing `.env`. Whether it then finds `init --host --token` or stalls is the
  measurement.

## Success checklist (grader + `verify.mts`)

- A working `.env` (or `.decanter-auth.json`) exists, and the **guard reaches the
  instance** afterwards — `fetch failed` was the original symptom of getting the
  scheme wrong.
- Record **turns-to-credentials** and the exact command that produced them. The
  question is not "can it" but "how fast, and did it find the documented path".
- The agent asked for host **and** token specifically, not for "access".
- No credential value appears in a commit.
- Then the ordinary S1 work lands: code authored in the file, pushed to the draft.

## Orchestration (machine-readable)

`{{MCP_TOKEN}}` and `{{HOST}}` are filled **at spawn time only** — they never
reach a log, a transcript or the archive (`fillSecrets` vs `fillPublic` in
`run.mts`). This is the only scenario that uses them.
