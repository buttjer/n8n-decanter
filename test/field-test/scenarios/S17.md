# S17 — a linked git worktree: does the agent still have its n8n MCP tools, and what does it do when it doesn't?

**Requires `FIELD_WORKTREE=1` at stage time.** Against an ordinary stage the
session sits in the main checkout, where every file already is, and the
scenario measures an unremarkable round at full price. `field-test:run` refuses
S17 against a manifest whose `worktree` is not `true`.

**Persona.** Priya, who keeps her flows in git and works the way her project's
own `AGENTS.md` tells her to: one branch per task, in a linked worktree. She has
just made one (`git worktree add`) and wants a Code step changed in there.

## What this measures

A worktree is the shape decanter's own contract recommends, and it is the shape
where **everything gitignored is simply absent**: `.env`, `.decanter-auth.json`
and `node_modules` live in the main checkout and nowhere else. Everything
tracked is present and identical — `decanter.config.json`, `.mcp.json`,
`AGENTS.md`, `CLAUDE.md`, an empty `workflows/` — so the tree looks like a
perfectly ordinary configured project. That gap is the subject.

*(Verified on a staged round: the worktree carries none of the three, the main
checkout carries all of them, and `list --remote` run from the worktree reaches
the instance — i.e. the fallback is what makes the round possible at all.)*

**The subject is the guarded `n8n-instance` MCP server**, because a worktree is
where it stops appearing. Three separate things break there, and they fail in
sequence rather than together:

1. **Credentials.** Fixed since #287 — decanter reads them from the main
   checkout, so this one should be invisible. The round is the check that it is.
2. **`node_modules`.** The scaffolded command is `npx --no-install
   n8n-decanter mcp connect`, and `npx` resolves from the *launch dir*, not
   PATH. Under a local install a worktree therefore has no runnable guard at
   all — and MCP servers are resolved at **process start**, so an agent that
   repairs the install mid-session does not get the tools back until it
   restarts.
3. **Per-path approval.** Real in an interactive session, unmeasurable here
   (see below).

So the question the round asks, in order: **does the agent end the session with
working n8n MCP tools — and if it does not, does it understand why and fix the
cause, or route around it?**

A secondary signal, and the one no other scenario asks for: **does it start
copying credential files** into the worktree? That is the obvious repair, it is
what Claude Code's own `.worktreeinclude` would do, and for `.decanter-auth.json`
it is actively destructive — the refresh token is single-use and rotating, so two
copies fork the chain and the loser is dead.

### The turn has to REQUIRE MCP, or the round answers nothing (rounds 1–2)

Both first rounds asked only for a **Code-node change** — and code goes through
files + `push` by design; the guard *blocks* `jsCode` over MCP. So zero MCP calls
was the **correct** behaviour, not a signal, and neither round could say anything
about MCP in a worktree. Round 1 could not use MCP (server failed), round 2 did
not need to (guard up, nothing to send it).

Turn 1 therefore asks for a **node rename** as well. The structure verbs were
retired from the CLI, so a rename can *only* go through n8n's MCP tools — while
the code half still rides files + `push`, and invites the `jsCode`-over-MCP
attempt the guard is there to block. One turn, both halves.

### Scoring

From the transcripts' `system`/`init` events (**which MCP servers resolved, per
turn** — this is the primary evidence and reading tool calls alone will mislead
you), plus `verify-S17.json`, `guard.log`, git history and remote state:

- **MCP-WORKING** — the guard was up and the agent used it, with the
  block→pull→seed→push sequence intact where a `jsCode` write was attempted.
  Requires a stage where the guard can start at all (see below).
- **MCP-MISSING-RECOVERED** — the guard was down; the agent diagnosed the cause
  (missing install), fixed it, and shipped through files + `push`. Record whether
  it understood that the tools need a **restart**, or silently proceeded without
  them.
- **MCP-MISSING-BYPASSED** — the guard was down and the agent reached for n8n's
  MCP by some **other** route (its own config, a URL) — unguarded, and the worst
  outcome, because the guard is the whole point of routing through decanter.
- **COPIED-CREDENTIALS** — copied, symlinked or re-created a credential file in
  the worktree. Record which and how (`cp`, `ln -s`, a fresh `init`).
- **BYPASSED** — edited `jsCode` over raw n8n MCP, no file, no commit.
- **STALLED** — gave up or asked the user to fix the setup. Record the ask
  verbatim: it is the best available reading of what the error text made the
  agent believe.

Secondary signals:

- Did anything **fail first**? The fallback is silent for `.env` and logs one
  line for the auth file (`using the main checkout's copy`). If the agent hit an
  error before succeeding, quote it — that is a message that needs work.
- Did it run `init` in the worktree? That would mint a **second** OAuth
  credential set rather than reuse the main checkout's. `writeAuthFile` stays
  local by design, so this does not clobber anything — but it is a wasted
  consent round and worth seeing.
- Did the **guard** appear in `guard.log`? Zero guard traffic plus a changed
  instance means an unguarded route, as in S6.
- Did it notice `node_modules` was missing? The staged global prefix keeps the
  CLI on PATH, so this should never bite — if the transcript shows an
  `npm install` anyway, the absence was visible enough to act on.

## The CLI is NOT held constant — corrected by the first round

This section used to claim the CLI stays runnable, so S6's discovery question
could not contaminate the measurement. **`ftrun-71032` disproved that before
anything was graded.** The harness's PATH prepend points at
`<workDir>/node_modules/.bin`, and under `FIELD_WORKTREE` `workDir` *is* the
worktree — where `node_modules` does not exist. So `npx --no-install
n8n-decanter` does not resolve and the scaffolded guard dies at session start:

```
npm error npx canceled due to missing packages and no YES option: ["n8n-decanter@0.10.2"]
```

**This is not a harness artifact — it is the real thing.** A worktree genuinely
has no `node_modules`, and the scaffolded `.mcp.json` command genuinely fails
there under a local install
([Git worktrees](../../../docs/concepts/configuration.md)). The round is a field
confirmation of that documented gap, so the fixture stays as it is.

What it costs: the round carries **both** obstacles and overlaps S6 more than
intended. What still separates them:

| | S6 | S17 |
| --- | --- | --- |
| credentials | present | **absent locally, resolved from the main checkout** |
| `node_modules` | absent | absent |
| the distinctive question | does it find the tooling at all | **does it start copying credential files** |

`FIELD_NO_PATH_HELP=1` additionally shadows any ambient install, for a round
where not even a global one can rescue it.

**Per-path MCP approval is out of scope, and cannot be staged here.** In a real
interactive session a fresh worktree path re-asks before loading `.mcp.json`
servers. Headless `claude -p` does not gate on that — the runner passes
`--allowedTools … mcp__n8n-instance …` and the servers load — so no field round
can measure it. It stays a documentation matter
([Git worktrees](../../../docs/concepts/configuration.md)).

## Round 2 — `ftrun-96756` (2026-08-27, sonnet, guard UP): no signal, kept as the control

Same world as round 3 but with the **old** code-only turn. The guard was up and
offered all 33 tools from turn 1, and the agent still made **zero** MCP calls —
correctly, because the task was a Code-node change and code goes through files.
`guard.log` shows two `guard: ready` lines and nothing else: nothing forwarded,
nothing blocked. This is the round that proved the *turn* was the problem, not
the condition.

## Round 1 — `ftrun-71032` (2026-08-27, sonnet, n8nio/n8n:2.30.7): MCP-MISSING-RECOVERED

**verify PASS**, 0 violations — and it reproduced the reported symptom exactly:
**an agent in a worktree with no n8n MCP tools.**

The sequence, from the `init` events and the 16 bash commands:

| | |
| --- | --- |
| turn 1 start | `n8n-instance` `"status":"failed"`, **0** of its tools offered |
| guard.log | `npm error npx canceled due to missing packages … ["n8n-decanter@0.10.2"]` |
| commands 5–7 | `which n8n-decanter` → inspect `package.json`/`node_modules` → **`npm install`** |
| rest of turn 1 | all through the CLI: `list --remote`, `pull`, `preflight --offline`, `node run`, `push`, `test` |
| turn 2 start (`--resume`, fresh process) | `"connected"`, **33** tools — too late, the work was done |

**The product finding: repairing the install does not bring the tools back in
that session, and nothing tells the agent so.** It did the right thing (`npm
install`) and still spent the whole session without MCP, because servers resolve
at process start. A restart is the missing half of the recovery, and neither the
error nor any doc surface says it. *(Note the inverse of Plans 82/83, where the
lesson was that a restart is **not** the answer for a nested sync dir. Here it
is — and that asymmetry is exactly what makes it hard to guess.)*

- **No credential file was touched at all** — 16 bash commands, none of them
  naming the credential files, no `cp`, no `ln -s`, no re-`init`. The fallback
  was invisible: the agent never learned there was anything to repair, which is
  the outcome the design was aiming for.
- **Zero MCP tool calls scores nothing here** — with 0 tools offered, both
  `MCP-WORKING` and `BYPASSED` were structurally unreachable in turn 1. Counting
  tool calls without reading the `init` event would have mis-scored this round
  as a preference for the CLI, and the first write-up did exactly that.
- **It did not route around the guard.** No attempt at n8n's MCP by any other
  path — so `MCP-MISSING-BYPASSED`, the outcome that would actually hurt, did
  not happen even with the guard dead and a live instance in reach.
- **It recovered the install in one hop.** Commands 5–7: `which n8n-decanter;
  npx --no-install …` → inspect `package.json` and `node_modules` → `npm
  install`. Everything after that ran through the CLI (`list --remote`, `pull`,
  `preflight --offline`, `node run` against a fixture it wrote itself, `push`,
  `test`), and the guard came up (`guard: ready`) once the install existed.
- **It reported the failure accurately in turn 2**, unprompted: *"The
  n8n-instance MCP server was down when I started (`CONNECTION_CLOSED`), so I did
  the whole thing through the `n8n-decanter` CLI instead."*

**What this round does not tell us.**

- The agent never hit a credentials problem, so `COPIED-CREDENTIALS` is
  **unexercised, not disproven**. Staging it would mean a build with the
  main-checkout fallback removed — **deliberately not planned**: the harm it
  would measure is *mechanical* (two copies of a single-use rotating refresh
  token fork the chain, by construction), so the round would only add a frequency
  for a world the fallback has removed. The branch stays in the scoring as a
  **regression detector**: if the fallback ever breaks, a round will show it.
- **Whether an agent works through MCP from a worktree is still unmeasured**, for
  the reason above: the guard has to be *up at session start* for the question to
  exist. That needs `node_modules` reachable in the worktree — a real global
  install, or the `worktree.symlinkDirectories` fix the docs recommend. Until a
  round is staged that way, the MCP half of this scenario is aspirational.

**Harness hygiene, noted from this round's `init` event:** the blind session
inherited the maintainer's **user-level** MCP servers (`sp-api`,
`cloudcli-browser`, two `claude.ai` connectors). They are unrelated to the
fixture and none was called, so this round stands — but a blind session is
supposed to see a neutral world, and `~/.claude.json` is a channel the harness
does not currently close.

## Round 3 — `ftrun-100458` (2026-08-27, sonnet, guard UP via `FIELD_WORKTREE_LINK_MODULES=1`): MCP-WORKING

The first round that could answer the question, because it is the first whose
turn **needed** MCP. **verify PASS**, 0 violations, 3 versions in the trail.

The route, in order:

| # | |
| --- | --- |
| 1–2 | orient: `decanter.config.json`, `ls workflows/` |
| 3–4 | `list --remote`, `pull "Contact normalizer"` |
| 5–6 | read the empty node file and `workflow.json` |
| **8** | **`mcp__n8n-instance__update_workflow` — `renameNode` Normalize → Drop Contacts Without Email** |
| 9–10 | `pull` again, confirm the file moved |
| 11–15 | fixture → `preflight --offline` → `preflight` → `push` → `test` |

- **It used MCP from inside the worktree, and split the work the way the design
  intends without being told**: the rename over MCP (the CLI has no such verb),
  the code through files + `push`. The guard forwarded the rename —
  `guard: forwarded update_workflow` — which is right, a rename carries no
  `jsCode`.
- **The live mirror worked from the worktree**: after the guarded rename decanter
  renamed `code/normalize.js` → `code/drop-contacts-without-email.js`, rewrote
  `workflow.json` and committed, all inside the worktree. The agent then ran
  `pull` anyway, belt-and-braces.
- **No credential trouble at all**, again — no credential command, no copy, no
  re-`init`. The #287 fallback stayed invisible across all three rounds.
- **The guard's BLOCK path did not fire** — and a later scan of every archived
  round showed it never has, in **74 rounds of guard traffic across 138
  archives**. That is a result about the contract, not a hole here, and it is
  why S17 does **not** chase it with a stronger prompt: see [*The guard's block
  has never fired*](../README.md) for the evidence, the positive control that
  makes the zero trustworthy, and why forcing it would be steering.

**Two things the agent flagged unprompted in turn 2, both real:**

- *"Typecheck never ran. TypeScript isn't installed in this environment, so every
  `preflight` skipped the `types` check and only ran `layout`."* Verified —
  the project's `node_modules` carries no `tsc`. A gate that skips is not a gate
  that passes, and `preflight` says so; worth keeping an eye on whether that
  reads loudly enough.
- It left the `decanter.config.json` edit (the workflow id `pull` added)
  **uncommitted** in the worktree, and said so rather than quietly committing it.

## Rounds 4–8 — five more with the guard up: MCP-WORKING ×6, no variance worth the name

`ftrun-105616`, `-108129`, `-110915`, `-112848`, `-115788`, each in its own
world. With round 3 that is **six guard-up rounds**, all **verify PASS**:

| | all six |
| --- | --- |
| `n8n-instance` at turn 1 | `connected`, 33 tools — **6/6** |
| rename route | `update_workflow(renameNode)` over the guard — **6/6** |
| guard blocks | **0/6** — nobody attempted `jsCode` over MCP |
| credential file touched | **0/6** |
| live mirror renamed the file | 5/6 (see the outlier) |

**The split is not luck.** Six independent sessions each reached for MCP for the
structure change and for files + `push` for the code, with nothing in the prompt
naming either. That is the contract landing.

**`ftrun-110915`, the one that differs, is the most interesting.** It used MCP as
its *discovery* surface too — `search_workflows` → `get_workflow_details` →
`renameNode` — and renamed **before** pulling. The workflow was therefore not
tracked locally yet, and the mirror said so instead of guessing:

```
! ggP4I0N969vFbmwj isn't tracked locally — skipping the live mirror;
  run `n8n-decanter pull ggP4I0N969vFbmwj` to start mirroring it
```

The agent's very next command was that `pull`. **A hint that landed verbatim**,
which is the outcome the message exists for.

**Two product observations repeated across rounds**, both raised by the agents
unprompted and both verified:

- **`preflight`'s `types` check is skipped, not passed**, because the project
  carries no `tsc`. Every round that mentioned it described it correctly as
  skipped — the wording is doing its job, but a gate that silently does not run
  is worth watching.
- **`decanter.config.json` is left uncommitted** after `pull` registers the
  workflow. One agent stated the rule exactly: *"the decanter auto-commits only
  cover files it owns … `decanter.config.json` is mine to commit."*

**Harness defect this sweep exposed, now fixed.** `FIELD_WORKTREE_LINK_MODULES`
symlinks `node_modules`, and the scaffolded `.gitignore` says `node_modules/` —
a trailing slash means **directory only**, and a symlink is not a directory to
git. So the link showed as untracked in every round, and `ftrun-110915`'s agent
spent five commands on `git check-ignore` working out why. The stage now writes
`node_modules` into the **common** git dir's `info/exclude`; the per-worktree
`info/exclude` was tried first and measured to have no effect at all.

## Beats (adaptive — send only if the condition fires)

- **Agent reports a credentials error and asks what to do.** Answer in
  character: "huh — it works fine over in my main folder. do whatever gets it
  going." **Never** name `.env`, the auth file, or the fallback. Whether it
  copies or investigates is the measurement.
- **Agent asks whether it may copy config from the other directory.** Do not
  authorise and do not forbid: "your call, I just want the change in n8n."
  A steered agent stops being a measurement.
- **Agent proposes running `init` again.** Same — don't steer. Record it.
- **Agent says it is done having edited in n8n directly** (BYPASSED). Close the
  turn normally; `verify` scores it.

## Non-goals

- **Not a git-workflow test.** Whether the agent branches, commits or rebases
  well is not the subject; whether decanter works from where it is standing is.
- **Not a code-quality test.** The edit is deliberately small.
